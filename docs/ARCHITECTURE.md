## Processing flow

1. Stream the upload to a job-specific temporary directory while enforcing limits.
2. Detect actual media type, calculate SHA-256, and collect safe metadata.
3. Decode an image once, or stream a video and sample frames with exact timestamps.
4. Detect and align faces for the face-focused deepfake model.
5. Run deepfake inference in batches and preserve per-face/per-frame scores.
6. Run ELA and LSB analysis on the original image or selected original video frames.
7. Aggregate deepfake frame results while retaining the most suspicious timestamps.
8. Store structured findings and generate visual evidence plus JSON/PDF reports.
9. Remove temporary uploads and frames according to retention configuration.

## Result contract

Every module returns a typed result with:

- `status`: completed, skipped, or failed.
- `version`: algorithm/model version.
- `settings`: thresholds and important parameters.
- `findings`: structured, machine-readable observations.
- `artifacts`: references to generated heatmaps or extracted inert bytes.
- `warnings`: limitations, quality problems, or unsupported conditions.
- `duration_ms`: measured execution time.

The evidence service preserves these module-level results. The primary deepfake model
may produce a calibrated probability, but ELA and LSB findings remain separate because
they do not estimate the same event.

## Video sampling policy

The first implementation uses configurable uniform sampling, for example one frame per
second, with a maximum frame cap. Later iterations may add scene-change frames and
denser sampling around suspicious intervals. Reports always state the policy so that
results can be reproduced.

## Storage model

| Entity | Key fields |
| --- | --- |
| AnalysisJob | ID, state, timestamps, source hash, media type, error summary |
| MediaInfo | dimensions, duration, codec, frame rate, metadata findings |
| ModuleResult | job ID, module name/version, status, settings, findings, warnings |
| FrameFinding | timestamp, frame index, face ID, score, artifact references |
| Report | job ID, format, generation time, path/checksum |

User media and generated artifacts are stored outside the database. Database records
use generated IDs and controlled relative paths, never raw user filenames as paths.

## Security boundaries

- Uploaded bytes are untrusted even when extensions look valid.
- Media decoding and metadata parsing are failure-isolated and resource-limited.
- Payload extraction is analysis only; extracted files are never executed.
- HTML/script-like payload previews are escaped or shown as plain hexadecimal/text.
- Temporary paths are generated by the application and cannot be selected by users.
- Logs exclude media content, extracted secrets, and unnecessary personal metadata.
